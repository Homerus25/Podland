# Frontend Conventions

How the React frontend (`frontend/src/`) is organized. System architecture lives in `docs/architecture-decisions.md`; domain language in `GLOSSARY.md`; API contracts in `doku/`. This file covers the patterns a new feature slice needs, so slices start from knowledge instead of re-reading sibling features.

Formatting is automated: a Crush pre-edit hook (`.crushrc` → `.crush/hooks/biome-format.sh`) runs Biome on a file before every edit, so files are already formatted when you read them. Run `./node_modules/.bin/biome check <changed files>` once at the end as a gate (`npx biome` does not resolve in this environment); never interleave `--write` runs with your own reads and edits. The gate is green on a clean tree — a red gate is always yours.

## Feature folder layout

Each feature lives in `src/features/<name>/`:

- `services/<feature>Api.ts` — API client functions through the shared axios instance (`@shared/utils/api`), plus the **DTO response types colocated here** (see the DTO-types note at the end of this file). Host-scoped request URLs route through the builder pair `hostApiPath`/`hostApiUrl` (`@shared/utils/api`), the single owner of host-scoped URL construction: it percent-encodes every path segment, hostId first — services never hand-encode. Axios calls take the path form (the shared instance prepends the base); fetch consumers (stream transport, `downloadFile`) take the full form. Stream and download URLs are consumed from the owning service's export (`pullStreamUrl`, `autoUpdateStreamUrl`, `volumeExportUrl`), never re-derived in hooks or components, and importing `apiBaseUrl` outside `@shared/utils/api` is off-limits (module-private; the compiler enforces it). Settled 2026-09-15 (architecture-review candidate C11).
- `hooks/<feature>Api hooks` — React Query hooks in `use<Feature>.ts`.
- `components/` — UI components and their colocated tests.

## React Query

- Query keys come from the `shared/queries` constructors (`containersQueryKey`, `secretQueryKey`, `hostStatusQueryKey`, the `hostsQueryKey` constant, …); never build a `['hosts', …]` array or a private key constructor in a feature. A new resource tab adds one `HostResource` union member plus one plural list constructor in `queryKeys.ts`.
- List-invalidating mutations go through `useListInvalidatingMutation(hostId, resourceOrResources, run)` (`shared/queries`); cross-feature or streaming invalidation calls `invalidateHostResources(queryClient, hostId, resourceOrResources)`. The factory is host-scoped by design: an app-wide resource has no host to scope to, so a feature whose mutations invalidate one app-wide shared key keeps a feature-local invalidating-mutation wrapper over that key instead of forking the factory (`useUsersInvalidatingMutation` in `features/users/hooks/useUsers.ts` over `usersQueryKey` is the reference). No optimistic updates (matches backend "list reflects server state" simplicity).
- The freshness vocabulary is owned by the query-side factory in `shared/queries` (`useFreshQuery.ts`), the twin of the list-invalidating mutation factory. A view that must always show the host's current state (a detail view, an inspect reveal, a stats snapshot) rides `useOneShotQuery(key, fetcher, { enabled })` — zero gcTime so the cache entry dies with the view, with an optional enabled gate defaulting to true for lazy fetches. An always-fresh list rides `useAlwaysRefetchListQuery(key, fetcher)` — refetch on mount "always", so a lazy-tab re-entry issues a fresh request inside the app-wide stale window while the cached list stays visible (no loading flash). The key always comes from the shared constructors and the query result passes through untouched; never hand-assemble `gcTime` or `refetchOnMount` in a feature hook. Values that must never be cached (revealed secrets) travel through `useMutation`, not `useQuery`.
- Row-scoped mutation state has one owner: `rowScoped` in `shared/queries` (`rowScopedMutation.ts`), the pure projection behind every row-action list. A list owns one mutation instance per lifecycle action (a plain row function cannot own hooks), and each row derives its own pending and error state from the mutation's `variables` through the projection: pending only for the row whose key the in-flight variables carry, the error only for the row whose key the variables still name — react-query keeps `variables` after settle, and that persistence is what makes the error scoping work — while every other row sees false/null and stays usable. The adapter hands over its key extractor explicitly at every call site: the shared identity extractor `identityKey` (exported beside `rowScoped` in `rowScopedMutation.ts`) for string-id variables (pods, containers, the hosts share section's revoke), a field accessor for object variables (quadlets' stop/restart read `quadletId`). No shape-sniffing, no default extractor; the module is pure — no hooks, no DOM, no QueryClient. The genuinely domain-local policies stay adapter code, unchanged: quadlets' disable-every-lifecycle-button while any action on the row is pending, the pods and containers sibling-reset ritual (`sibling.reset(); mutate(...)`), containers' error precedence between the toggle and restart errors, and the hosts share section's section-level error display. The projection's contract is pinned once in `shared/queries/rowScopedMutation.test.ts`; the feature lifecycle suites keep one adapter-wiring smoke each. Settled 2026-11-06 (architecture-review candidate 2).

## Components

- Every table-backed resource list renders through `ResourceList` (`@shared/components/ResourceList`), the one owner of the list plumbing: the loading/error/empty/table triad, the Chakra table chrome, the plural testid derivation (`{resource}s-loading`, `-error`, `-empty`, `-table`), the toolbar wrapper, and the permission hint. The triad itself is single-owned one level down, in `ResourceStates` (`@shared/components/ResourceStates`) — the headless loading/error/empty owner `ResourceList` composes for its triad branch, and non-table collection sites (card grids, grant rows) render through it directly instead of hand-deriving the ritual. It renders the three states and takes `children` for the populated state, owning the triad JSX, the copy defaults, the styling, and the testid derivation; it is deliberately non-generic (`items: readonly unknown[] | undefined` — the module never reads item shape, and undefined counts as empty) and has no loading-copy override. It is for collections, not detail views: single-item loading/error with no empty semantics (host detail, quadlet edit, secret detail) does not fit `items`. Settled 2026-10-01 (2026-09-22 architecture-review candidate 8). A feature list is an adapter: it keeps its query and mutation hooks and hands over resolved state — `resource` (plural noun), `isPending`, `error`, `items`, `columns` (data, not JSX: `{ label?, isNumeric?, isName?, sortBy? }[]`; a label-less entry renders the bare action-column header), `renderRow`, and optionally `toolbar`, `canManage`, `emptyMessage`, `onRemoveSelected`. Mobile pinning (spec 393) is module-owned off one marker: a list marks its name column with `isName`, and below `lg` the owner pins that column left and the trailing label-less action column right inside the table container's horizontal scroll — the pins reach the feature-rendered `<Td>`s (the owner clones the row's cells; spanning error cells are never pinned), so no feature hand-rolls sticky CSS. At `lg` and up the rendering is unchanged, and an unmarked list renders exactly as before. The pinning contract is pinned once in `shared/components/ResourceList.test.tsx`. `SecretList` (`src/features/secrets/components/SecretList.tsx`) is the smallest reference adapter; a new resource tab copies it, not the plumbing. Column sorting is module-owned: a column's optional `sortBy` accessor — `(item: T) => string | number` — extracts the row's sort key, and clicking a sortable header cycles asc, desc, unsorted (returning to the server's natural order); the first click on any column is asc, and there is no default sort. The active column carries `aria-sort="ascending"|"descending"` (unsorted columns carry no `aria-sort`) plus a direction arrow (▲ asc, ▼ desc); sortable headers get `cursor="pointer"` and `data-testid="sort-{resource}-{columnIndex}"`, while columns without `sortBy` (action columns) render as plain non-clickable headers. String keys compare with `localeCompare`, number keys numerically — the key's runtime type picks the comparison. Sort state is component-local and resets on unmount. Sort behavior is pinned once, in `shared/components/ResourceList.test.tsx` (the three-state cycle, the aria-sort contract, string and numeric reordering, non-sortable columns, the remount reset); each feature list suite keeps one smoke test — clicking a header reorders rows. Row selection (spec 461, ticket 463) is module-owned the same way, and opt-in: a list passes `selection` — `{ getKey: (item: T) => string; onChange?: (selectedKeys: string[]) => void }` — where `getKey` is the row's stable identity (the container/image/pod/quadlet `id`, the volume/network/secret `name`), never the row index, so the selection survives sorting and refetches. The owner keeps the selected-key set as component-local state beside the sort state, so it resets on unmount like the sort; a list that passes no `selection` renders exactly as before. The checkbox column is the owner's, not the feature's: the same cell-cloning walk that owns mobile pinning prepends a leading checkbox `<Td>` to each data row and a select-all `<Th>` to the header, so no feature row grows a cell — and a row whose cells span columns (the container, pod, and quadlet row-error rows) is a spanning row, not a data row: it gets no checkbox, and its `colSpan` grows by one while selection is on so the table stays valid. The checkbox column is a middle column and is never a pin target; the pin indices stay in column space. The header checkbox is a toggle over every row — select them all when they are not all selected, clear when they are. Checkboxes render only on an explicit selection grant: `canManage === true`, or the adapter's `canSelect` when its selection action rides a lower capability than its toolbar's write gate (spec 486, ticket #491 — the containers list's bulk connect rides `manage-networks` while its toolbar rides `manage-containers`, so it passes the union and a network-only admin gets the checkboxes and the connect button without the container-write toolbar, the adapter gating its own Create/Prune on the write grant; a caller below both capabilities keeps the hint). An omitted `canManage` means "ungated" for the toolbar (which then renders), but it is not a write grant, so a list that asks for selection without saying who may write renders no checkboxes rather than offering a read-only caller an action that would 403. The adapter reads the live selection without keeping a copy of it: the owner renders the toolbar's "Remove selected" button itself — label, red outline, derived testid (`remove-selected-{plural}-button`), and its place leading the toolbar row's left-edge group — the group that also holds the adapter's own selection actions — ahead of the adapter's right-aligned toolbar, so the placement cannot drift per feature. The button renders permanently for a write-capable caller — never gated on a non-empty selection, disabling itself while nothing is selected, the same always-visible self-disabling pattern the adapter's own selection actions use (ticket #493, reversing spec 461's "no disabled button, ever") — and only on the toolbar's write grant — `canManage === true`, never the wider selection gate a `canSelect` list opens for its own action, because removal is a write act even on a list whose connect action rides a lower capability. The adapter opts in with `onRemoveSelected`, a handler receiving the exported `ResourceListSelectionState<T>` — `{ selectedKeys, selectedItems, clear, clearKeys }`, where `selectedItems` is the selection projected onto the current rows in the list's current order (so a sorted list reports its selection sorted), `clear` is the post-mutation reset the adapter calls once a bulk action has removed the rows, and `clearKeys(keys)` is the partial reset a batch run needs (spec 486, ticket #487): it drops exactly the named keys, so a bulk transfer clears only the items that succeeded and leaves the failures selected for the retry — both resets go through the same `applySelection`, so `onChange` fires either way; `onChange` is the reaction seam for adapters that must act on every change. A list's own selection-driven toolbar buttons ride `selectionActions` — `(selection: ResourceListSelectionState<T>) => ReactNode` — rendered in the same left-edge group as the owner's Remove selected button, for a selection-capable caller only (`canManage === true`, or the adapter's `canSelect`) and ALWAYS, never gated on a non-empty selection: the adapter's buttons disable themselves on an empty selection, because a bulk action's button must stay visible so the user knows it exists and where (spec 486). Read-only callers keep the permission-hint swap untouched, so the seam itself needs no extra gating — but an adapter may still gate its own button on a different capability than the toolbar's write gate, in either direction: the secrets transfer rides `reveal-secrets` (admin), a HIGHER bar, because a secret's value leaving the host is a reveal, while the toolbar's write gate is `manage-secrets`, so that button renders for every write-capable caller and disables itself with the admin reason; the containers bulk connect rides `manage-networks`, a LOWER bar than the toolbar's `manage-containers`, so the list passes `canSelect` (the union) and the button renders for a network-only admin too. The accessible names are derived — `Select all {plural}` on the header checkbox, `Select {key}` on a row's — so suites query by role, not by testid. The selection contract is pinned once in `shared/components/ResourceList.test.tsx` (opt-in, per-row toggle, select-all in both directions, the `onChange` payload, the owner-rendered Remove selected button — left placement, live-selection payload, `clear` — the read-only gate, the remount reset, survival across a sort, the spanning-cell `colSpan` growth, the checkbox column never pinning, and the selection-actions seam: permanent render for a selection-capable caller, absent for a read-only one, the `canSelect` gate rendering the seam below the toolbar's write grant while Remove selected stays on it, the live selection handed over, and `clearKeys` dropping only the named keys); feature list suites keep adapter-wiring smokes only. Two consequences of the cell-cloning walk bind every adapter: `renderRow` must hand back a `Tr` (or a `Fragment` of `Tr`s) — a row wrapped in a component element is opaque to the walk, so it silently loses both the pins and the checkbox column, which is why a feature row is a plain function returning its `<Tr>` (`renderVolumeRow` in `VolumeList` is the reference) — and the owner's checkbox cell stops the click from reaching the row, so a clickable row never navigates when the user is only selecting it.
- The triad is **inline, never an early return**: the toolbar (or hint) renders above the state ternary, so toolbar and hint stay reachable while loading, on error, and when empty. Do not add a loading early-return to a list component.
- Errors render via `ErrorDisplay` with `getApiError(error)`; it accepts extra props (e.g. `data-testid`) and spreads them onto the alert. `ResourceList` uses it for the list-level error state; feature code keeps it for row- and dialog-level errors.
- Every mutation dialog renders through the shared dialog module at `@shared/components/MutationDialog`: form dialogs through its `FormDialog` preset, destructive confirms through its `ConfirmDialog` preset (ghost cancel, red confirm with the `confirm-delete-button` testid, pending wired). The module owns the plumbing every dialog used to hand-roll: the modal shell, the reset invariant (`reset()` runs on mount and unmount; consumers render the dialog conditionally, so mount is open and unmount is close, and reopening always starts clean), pending wiring, close-on-success, and the in-modal error region. It never touches react-query: the caller keeps its mutation hooks (and invalidation choices) and hands over the result's structural slice `{ mutate, isPending, error, isSuccess, reset }`. Settled 2026-09-11 (architecture-review candidate C6).
- Exception — a multi-phase chained flow that no `MutationDialog` preset fits (chained mutations with a read-only middle phase, where the phases share one modal and the footer changes per phase) is a feature-owned modal over the shared `Modal` shell (`@shared/components/Modal`), not a fork of the dialog module: the feature owns the phase state host, the per-phase footer, and the reset invariant (conditional render — mount is open, unmount is close — so reopening always starts clean), and keeps its mutation hooks and invalidation choices as usual. `AutoUpdateModal` (check-then-run report) and `ImportComposeModal` (spec #336: input → read-only preview → install report) are the precedents. Settled 2026-10-20 (spec #336 review).
- Stay-open report dialogs — a mutation whose success payload is rendered in place — ride `ReportDialog` (`@shared/components/ReportDialog`), standalone from `MutationDialog` because the two disagree on the headline invariant (stays open on success vs closes on success). It owns the skeleton both surfaces share: the modal shell, the reset lifecycle, the confirm/report footer swap, the pending wiring, the error region, the report table's chrome, and the optional force-retry button. The caller hands over the structural slice with its variables (`mutate: (variables: TVariables) => void`, `void` for a mutation that takes none), the copy (confirm and report titles, confirm label and testid, close testid), the first pass's variables (`confirmVariables` — always the plain request), an adapter-owned confirm body, the report headers, the entry key, the failure predicate (`entryFailure`), the entry cells (`renderEntry`, which receives the failure the module already derived so the table and the retry can never disagree), and the empty-report node. The force retry is one optional seam: `forceRetry: { label, testId, variables }` renders a footer button only when the report actually holds failures, and its `variables` receive exactly the failed ids — the first pass is plain, the retry carries `force=true`, and a resource with no force path (secrets) passes no `forceRetry` at all, so "no retry" is the absence of the seam rather than a disabled button. `PruneReportDialog` (`@shared/components/PruneReportDialog`) is now the prune adapter over it — the `void`-variables case, keeping prune's noun-derived copy, testids, and reclaimed-size column — and the images prune adapter in `ImageList` is the smallest reference adapter for that surface. The bulk-remove surface (spec 461, ticket #468) has one adapter for all seven resources: `BulkRemoveDialog` (`@shared/components/BulkRemoveDialog`) owns the copy, the selected-names list, the report chrome, the force retry and every testid, and each list hands it only its noun, the item key and the item label. It captures its id→label map when the dialog opens, because the list clears its selection once the run succeeds — through the skeleton's `onSuccess` seam, fired once per completed run (the first pass and each retry) the moment the report arrives, never on close, so a failed run keeps the selection. The toolbar's "Remove selected" button is not the dialog's either — `ResourceList` owns it (see the ResourceList bullet), outside the dialog.
- Stay-open transfer dialogs — a cross-host move/copy whose success narrates in place (quadlet, volume, secret, image) — ride the transfer-dialog preset at `@shared/components/TransferDialog`, the third dialog shape after `MutationDialog` and `PruneReportDialog` (issue 238's per-feature ruling ended when the third surface arrived; settled 2026-10-05, issue 241). The preset splits in two: `useTransferState(host, capability)` owns the state half — the capability-filtered target list (source excluded), the selected target defaulting to the first, and the mode defaulting to Move — and `TransferDialog` owns the render half: the target select, the mode radio (hidden when `pinnedMode` pins a copy-only surface — the image copy, issue 376), the target-scoped preview's pending/error/collision states, the confirm/report footer swap, and the in-modal error region with the `renderHints` seam (error-code hints live there, the `renderError` precedent). The referencing-quadlet warning is not the preset's own: it lives in `TransferReferencingWarning` in `@shared/transfers/transferPresentation`, shared by the single and batch dialogs. Like `PruneReportDialog` it stays open on success — a partial result names the both-hosts state — but the report node is the caller's: the adapter hands over `report` and decides what narrates, so a mixed success behavior (the quadlet's file-only close) stays feature-owned. The adapter calls `useTransferState` first (its preview hook needs `targetId`), keeps its domain in two body slots — `warnings` renders between the collision block and the referencing warning, `children` after it, preserving each surface's warning order — and passes `reset` only for a caller-owned mutation that outlives the dialog (component-local hooks die with it; the effect keys on the reference, so it is a react-query mutation's stable `reset`). The feature keeps its preview query key's constructor and fetcher and its mutation or stream hook as a thin adapter over the shared transfer-hooks module (`@shared/transfers`; settled 2026-10-13, issue 273, 2026-10-08 architecture-review candidate 5) — the module owns the preview ritual (the null-target guard, the empty-string placeholder key, the enabled gate), the both-hosts invalidation, and the move-stream lifecycle, while the feature keeps its domain: the event vocabulary, shape guard, progress fold, and URL builder. The hosts query inside `useTransferState` is the one query the preset owns. `MoveSecretDialog` is the smallest reference adapter. Settled 2026-10-19 (architecture-review candidate C6): a transfer adapter's domain splits into two colocated modules — the warnings module owns the pure preview projections and the warning lists as data-prop components (no queries, no hooks), and the report module owns the narration, the live progress, and the report precedence as an exported pure projection the adapter's close-on-success effect consumes — so the adapter keeps option state and confirm wiring only (`MoveQuadletDialog` is the reference split). Settled 2026-10-19 (architecture-review candidate C8): the transfer presentation rituals live in one module in the shared transfers kit (`@shared/transfers/transferPresentation`) — `transferProgressLabel` owns the phase vocabulary's labels (a skip without a reason renders plain "skipped", no dangling dash), the `TransferReport` skeleton owns the stay-open report's shape (the Moved/Copied header with the optional byte-count suffix, the partial block with the pinned both-hosts tail and the red error line, the children slot), and the body pieces the single and batch dialogs share live there too, so the batch dialog does not re-implement the single one's: `TransferTargetSelect` (the target select and its no-targets copy), `TransferModeRadio` (the mode radio, hidden when pinned), `TransferPreviewStates` (the preview's pending/error/collision states, parameterised by the testids each dialog uses), `TransferReferencingWarning`, the `TransferPreviewSlice` type they all read, and `partialOutcome` (the one "partial is a failure" mapping — each adapter keeps its own domain sentence) — while each adapter stays the wording owner of its domain cause sentence, narrations, and error-code hints (`MoveQuadletReport`, `MoveVolumeDialog`, and `MoveSecretDialog` are the reference adoptions). A transfer over a whole row selection rides the batch sibling, `MultiTransferDialog` (`@shared/components/MultiTransferDialog`; spec 486, ticket #487): the target host and the move/copy mode are chosen once for the batch, every selected item's preview and warnings render under its own name, nothing runs until the user confirms, and the confirm then runs the per-item requests sequentially in list order, client-side, over the existing per-item endpoints — no backend or API change — with the body becoming a per-item report. The module owns the batch ritual and nothing domain: the adapter hands over `MultiTransferItem[]` (its own row object, the selection key, the label, that item's preview slice, and its warnings node), a `runItem(item, context)` that maps its domain envelope to `{ ok, detail }`, and `onFinished(succeededKeys)`, which fires exactly once per completed run so the list can `clearKeys` only the successes. The streaming features run their per-item transfer through `runMoveStream` in the shared transfer-hooks module — the plain (non-hook) twin of `useMoveStream`, which delegates to it — because hooks cannot be called in a loop; `movePreviewQueryOptions` is the matching per-item preview seam, so a batch previews N items through `useQueries` over the same key constructor and fetcher the single-item hook uses. `MoveSecretsDialog` is the smallest reference adapter.
- Raw inspect JSON — the read-only report behind a resource's detail page (containers, networks, images, secrets; spec 287) — rides the detail-page layout's "show inspect JSON" reveal, not a dialog: see the Detail pages section below for the module, its query-hook contract, and the `Record<string, unknown>` report type.
- The connect ritual — attaching a running container to a network — has one owner: `ConnectDialog` in the networks feature (`@features/networks/components/ConnectDialog`), discriminated by the fixed side (the Networks tab passes the network and the dialog picks the container; the Containers tab passes the container and the dialog picks the network). The dialog fetches its own options and drives the connect mutation itself, including the both-lists invalidation that rides the mutation; every entry point shrinks to a button, the fixed side, and a close callback — five of them: the two list rows (the Networks tab's row button fixes the network, the Containers tab's fixes the container), the two detail pages' header actions (the network page's Connect container, the container page's Connect to network), which pass the same fixed side from their own DTO, and the Containers list's bulk selection action, which fixes the whole selection and also takes `onFinished`. The containers feature calls into the networks feature for connect, never the reverse, and the networks feature imports nothing new from containers for it. The dialog's third fixed side is the batch one (spec 486, ticket #491): the Containers list passes `containers` and the dialog picks ONE network for the whole selection, then runs the connects sequentially through `useSequentialConnect` — the plain hook beside the parallel `useConnectContainers` mutation, which stays the two single-fixed-side flows' transport — and narrates a per-item report, calling `onFinished(succeededKeys)` so the list clears only the containers that connected; closing mid-run aborts the in-flight connect and the abandoned run reports nothing, the batch transfer dialog's rule (spec 486 review). The containers list's row no longer offers Connect (the action set renders it only when its caller hands over `onConnect`), while the container detail page keeps it. Settled 2026-10-13 (2026-10-08 architecture-review candidate 6).
- Side effects are explicit at each call site through the seams: `onSuccess` fires exactly once before the module closes the dialog (a toast, a navigate-away, or a silent close is a per-site choice, never a copy-paste accident), and `onError` fires on failure while the dialog stays open. A form's submit handler just calls `mutate`: forms no longer await their mutations and carry no internal error JSX or reset calls.
- The error region renders `ErrorDisplay` with `getApiError(error)` under the `mutation-dialog-error` testid by default; `renderError` replaces the whole region, and that is where error-code-to-hint mapping lives as feature adapters (volume composes the default display plus its in-use hint, populate maps `VOLUME_UPLOAD_TOO_LARGE`). On `ConfirmDialog`, `renderConfirm` replaces the confirm button itself (the force-refusal preset's swap, below).
- The force-refusal confirm ritual — a destructive delete the server can refuse with a specific error code (an in-use image, a pod with running containers) — has one owner: the `ForceConfirmDialog` preset in the shared dialog module, composing `ConfirmDialog`'s existing `renderError`/`renderConfirm` seams (no new seams; `ConfirmDialog`'s contract is unchanged). The preset owns the ritual: the refusal-code predicate, the orange hint replacing the error region (the shared `ErrorDisplay` for every other error), the confirm-to-force footer swap to the outline force button, the pending wiring, and the force flag keyed off the current error — the first confirm sends the plain request, and only after the refusal does the retry carry `force=true`. The adapter keeps its domain vocabulary only: the refusal code, the hint copy and its testid, the labels, the force button's testid, and the payload builder taking the force flag. The images delete modal and the pods remove modal are the reference adapters. Settled 2026-10-24 (2026-10-24 architecture review, ticket 358).
- The dialog module owns every confirm and form footer, extending the C6 settlement. Destructive confirms keep riding `ConfirmDialog`, now with `confirmColorScheme`/`confirmTestId` knobs so "confirm-with-variables" stops meaning "destructive" (defaults stay the red `confirm-delete-button` look, byte-identical). Confirms that perform a caller-owned action instead of a mutation ride `ActionDialog` — shell + ghost Cancel only: no pending wiring, no error region, no auto-close; the caller closes in `onConfirm` (the update-all pre-flight is the reference). Form dialogs ride `FormDialog` with fields-only bodies: the body's form carries the id and its submit handler just calls `mutate`; the footer's blue submit is associated by native form id, and one submit policy holds everywhere — disabled while the published form state (`FormValidityScope`, passed straight from the form library's `formState`) is invalid or submitting, or while the mutation is pending. The formerly ungated forms (create container, quadlet create/edit, add host) validate on change now, so their buttons start disabled — a deliberate normalization, not drift. The one non-dialog form site (the host settings inline form) joins through the composable `FormFooter` without a shell: it keeps submit-time validation, its submit gates on the host mutation's `pending` — the single prop the site keeps because its mutation lives in the host tab — and its Cancel (opt-in `cancelTestId`, `host-form-cancel` there) reverts the fields to the stored seed and fires the host's cancel seam, whose mutation reset clears both the error text and the "Changes saved" banner; cancel stays enabled while a save is in flight, and because a cancelled save still runs to completion server-side, the host tab suppresses that late settle so neither banner nor error resurrects over the reverted fields. Skeleton and invariant behavior of all these surfaces is pinned once in `shared/components/MutationDialog.test.tsx`; feature suites keep domain assertions only. Settled 2026-09-25 (2026-09-22 architecture-review candidates 3 and 7).
- The key/value row-editor ritual — the mono key/value inputs, the per-row remove buttons, and the add button over a `useFieldArray` — has one owner: `KeyValueEditor` (`@shared/components/KeyValueEditor`). The module renders the rows and buttons and owns the optional per-row key validation (`requireKeyWithValue`, default off: a key is required when the row's value is set). The rows-to-record mapper `keyValueRowsToRecord` (empty-key rows skipped, `undefined` when no row is filled, duplicate keys collapse to the last value) is the ritual's pure half and lives in `@shared/utils/keyValueRows` — its one owner — so the adapters and the payload builders in the feature services modules (which never import components) all import it from there. The adapter owns the form and `useFieldArray` and hands over the field-array return plus `register` and the per-row key error; the module never calls form hooks. Testids derive from a singular `noun` prop (`add-<noun>`, `remove-<noun>-<index>`), the add button's copy from `addLabel`, and the per-row aria labels from `keyAriaLabel`/`valueAriaLabel`/`removeAriaLabel`. The create-container page's environment rows, the create-volume dialog's labels and driver-options rows, and the create-pod dialog's labels are thin adapters over it. ## Streaming

- Every streaming endpoint rides the stream transport module (`@shared/streaming/streamTransport`); no feature hand-rolls a streaming fetch, an abort lifecycle, or a terminal guard. The two layers split by streaming shape: operation streams — a start/cancel lifecycle whose backend ends runs with a terminal `complete`/`error` event (image pull, quadlet auto-update) — use the `useNdjsonOperation` hook, which owns the abort, the supersede rule (a new start aborts the old run, whose late events reach nobody), exactly-one-terminal, and the running/error state; signal-driven follow streams without operation semantics (log following) call the `streamNdjson` function directly and pass their own `AbortSignal`. The event loop and the terminal semantics those runs share live in one plain runner, `runNdjsonOperation` — every value dispatched until the first terminal, which ends dispatch so a second terminal or any late event reaches nobody — and the hook delegates to it; the transfer kit's plain move runner (`runMoveStream`) delegates to the same function, so a batch transfer and the operation flows cannot drift on terminal semantics (spec 486 review). The state wiring around the loop stays the owning hook's — `useNdjsonOperation` for the operation flows, the transfer kit's `useMoveStream` over `runMoveStream` for the move streams, whose progress/result state the transport's hook shape does not carry. A feature keeps only its event handlers, shape guards, and invalidation choices — the Bearer preamble, the error envelopes, the abort teardown, and the NDJSON consume loop (malformed lines warned and skipped) are the module's. ## Auth and 401s

- "Refresh the session" has one owner, `refreshSession()` in `@shared/utils/api`: it alone assembles the POST literal, installs the fresh token, and holds the single flight every caller shares; success resolves the payload, any failure (auth rejection or network) resolves `null` without throwing or firing the seam. - 401s are owned by the shared session policy, never by a feature: the axios response interceptor on the shared instance (`@shared/utils/api`) and the stream transport both route through `handleUnauthorized` — single-flight refresh, replay once, session death when refresh or replay fails. - **The detail page's header action row has one owner: `headerActionGroup({ actions, remove })`** in the detail kit (`@shared/components/detailKit`), beside `removalAction` — the six resource detail pages compose their header actions through it instead of hand-rolling the gate ritual, so the group's composition, the read-level rule, and the empty-group contract cannot drift between them again. The kit's tri-state cascade answers the actions that carry a `gate` directly — Remove, the container page's edit-configuration and connect hint, the network page's connect, the secret page's move, the image page's copy. An action whose control is a shared action-set component — the container and pod lifecycle sets, the volume Move/Copy and Populate sets — rides one ungated control whose buttons self-gate on a collapsed `gate === "allowed"` boolean inside that component, so the gate ritual for those actions is the action-set component's, not the kit's. Each action is a `HeaderAction`: an optional `gate` (the `useCapabilityGate` tri-state that answers it), an optional `hint` (what a denied caller reads), and a `control` (what an available caller gets). The tri-state answers each action exactly as the Remove cascade does — `allowed` renders the control, `denied` renders the action's own hint if it has one and nothing otherwise, `pending` renders neither (never flash the read-only hint at a write-capable caller) — and an action with no `gate` at all is read-level, so its control renders for every caller whatever the gate says: Logs, Download, and Export never disappear behind a write gate that is still deciding. A falsy control is dropped, which is how a page self-gates an action on its overview DTO having loaded (`network ? <Button/> : null`) — a not-found page renders no control that would open nothing. `remove` renders last, and the group is `undefined` — not an empty fragment — when nothing renders, because a bare fragment is always truthy and would leave an empty `detail-page-header-actions` row behind. The one-hint rule: a detail page's header renders at most one hint per capability, and the Remove cascade already renders the page's write hint on denied, so an action gated on that same capability passes no `hint` — otherwise a denied caller reads the identical sentence twice (three times on the container page). Only a genuinely different capability keeps its own hint: the container page's `manage-networks` connect (whose copy names networks) and the secret page's `reveal-secrets` admin move (Remove is write-level there). The container details page is the reference adapter. Settled 2026-11-06 (spec #477 code review, findings F1–F4).
