# Frontend Conventions

How the React frontend (`frontend/src/`) is organized. System architecture lives in `docs/architecture-decisions.md`; domain language in `CONTEXT.md`; API contracts in `doku/`. This file covers the patterns a new feature slice needs, so slices start from knowledge instead of re-reading sibling features.

Formatting is automated: a Crush pre-edit hook (`.crushrc` → `.crush/hooks/biome-format.sh`) runs Biome on a file before every edit, so files are already formatted when you read them. Run `npx biome check <changed files>` once at the end as a gate; never interleave `--write` runs with your own reads and edits.

## Feature folder layout

Each feature lives in `src/features/<name>/`:

- `services/<feature>Api.ts` — API client functions through the shared axios instance (`@shared/utils/api`), plus the **DTO response types colocated here** (see the DTO-types note at the end of this file). Machine-scoped request URLs route through the builder pair `machineApiPath`/`machineApiUrl` (`@shared/utils/api`), the single owner of machine-scoped URL construction: it percent-encodes every path segment, machineId first — services never hand-encode. Axios calls take the path form (the shared instance prepends the base); fetch consumers (stream transport, `downloadFile`) take the full form. Stream and download URLs are consumed from the owning service's export (`pullStreamUrl`, `autoUpdateStreamUrl`, `volumeExportUrl`), never re-derived in hooks or components, and importing `apiBaseUrl` outside `@shared/utils/api` is off-limits (module-private; the compiler enforces it). Settled 2026-09-15 (architecture-review candidate C11).
- `hooks/<feature>Api hooks` — React Query hooks in `use<Feature>.ts`.
- `components/` — UI components and their colocated tests.

## React Query

- Query keys come from the `shared/queries` constructors (`containersQueryKey`, `secretQueryKey`, `machineStatusQueryKey`, the `machinesQueryKey` constant, …); never build a `['machines', …]` array or a private key constructor in a feature. A new resource tab adds one `MachineResource` union member plus one plural list constructor in `queryKeys.ts`.
- List-invalidating mutations go through `useListInvalidatingMutation(machineId, resourceOrResources, run)` (`shared/queries`); cross-feature or streaming invalidation calls `invalidateMachineResources(queryClient, machineId, resourceOrResources)`. The factory is machine-scoped by design: an app-wide resource has no machine to scope to, so a feature whose mutations invalidate one app-wide shared key keeps a feature-local invalidating-mutation wrapper over that key instead of forking the factory (`useUsersInvalidatingMutation` in `features/users/hooks/useUsers.ts` over `usersQueryKey` is the reference). No optimistic updates (matches backend "list reflects server state" simplicity).
- Detail views that must always refetch use `gcTime: 0`. Values that must never be cached (revealed secrets) travel through `useMutation`, not `useQuery`.

## Components

- Every table-backed resource list renders through `ResourceList` (`@shared/components/ResourceList`), the one owner of the list machinery: the loading/error/empty/table triad, the Chakra table chrome, the plural testid derivation (`{resource}s-loading`, `-error`, `-empty`, `-table`), the toolbar wrapper, and the permission hint. A feature list is an adapter: it keeps its query and mutation hooks and hands over resolved state — `resource` (plural noun), `isPending`, `error`, `items`, `columns` (data, not JSX: `{ label?, isNumeric? }[]`; a label-less entry renders the bare action-column header), `renderRow`, and optionally `toolbar`, `canManage`, `emptyMessage`. `SecretList` (`src/features/secrets/components/SecretList.tsx`) is the smallest reference adapter; a new resource tab copies it, not the machinery.
- The triad is **inline, never an early return**: the toolbar (or hint) renders above the state ternary, so toolbar and hint stay reachable while loading, on error, and when empty. Do not add a loading early-return to a list component.
- Errors render via `ErrorDisplay` with `getApiError(error)`; it accepts extra props (e.g. `data-testid`) and spreads them onto the alert. `ResourceList` uses it for the list-level error state; feature code keeps it for row- and dialog-level errors.
- Every mutation dialog renders through the shared dialog module at `@shared/components/MutationDialog`: form modals through `MutationDialog`, destructive confirms through its `ConfirmDialog` preset (ghost cancel, red confirm with the `confirm-delete-button` testid, pending wired). The module owns the machinery every dialog used to hand-roll: the modal shell, the reset invariant (`reset()` runs on mount and unmount; consumers render the dialog conditionally, so mount is open and unmount is close, and reopening always starts clean), pending wiring, close-on-success, and the in-modal error region. It never touches react-query: the caller keeps its mutation hooks (and invalidation choices) and hands over the result's structural slice `{ mutate, isPending, error, isSuccess, reset }`. Settled 2026-09-11 (architecture-review candidate C6).
- Stay-open report dialogs — a mutation whose success payload is rendered in place (prune) — ride `PruneReportDialog` (`@shared/components/PruneReportDialog`), standalone from `MutationDialog` because the two disagree on the headline invariant (stays open on success vs closes on success). It owns the reset lifecycle, the confirm/report footer swap, the report table (mono label cell, red error cell vs `formatBytes`), the empty-report and confirm copy derived from the singular `resource` noun, and the error region. The caller hands over the structural slice plus the success payload (`data: TEntry[]`), the noun, and the two entry accessors `entryKey` and `renderLabel`; the images prune adapter in `ImageList` is the smallest reference adapter. Toolbar labels stay feature-owned — they live outside the dialog.
- Side effects are explicit at each call site through the seams: `onSuccess` fires exactly once before the module closes the dialog (a toast, a navigate-away, or a silent close is a per-site choice, never a copy-paste accident), and `onError` fires on failure while the dialog stays open. A form's submit handler just calls `mutate`: forms no longer await their mutations and carry no internal error JSX or reset calls.
- The error region renders `ErrorDisplay` with `getApiError(error)` under the `mutation-dialog-error` testid by default; `renderError` replaces the whole region, and that is where error-code-to-hint mapping lives as feature adapters (volume composes the default display plus its in-use hint, image returns only the in-use hint, populate maps `VOLUME_UPLOAD_TOO_LARGE`). On `ConfirmDialog`, `renderConfirm` replaces the confirm button itself (image's `confirm-delete-button` to `force-delete-button` swap driven by the error).
- Reference adapters: `SecretList`'s delete confirm is the smallest confirm; `MachinesPage`'s add-machine modal is the smallest form host. Copy those, not the machinery. Non-modal mutation sites (secret reveal, share grant/revoke, the machine settings inline form, the quadlet lifecycle menu, the pull-image toolbar) keep feature-local resets; they share no dialog skeleton with the module.
- Rows are feature-rendered: the Row component owns the singular `data-testid` (`<item>-row`) so tests use `within(row)` for per-row assertions. When several of a list's rows render on one page (the users directory), the testid carries the row's unique key — `user-row-${username}`, the `grant-row-${id}` precedent — so tests still select one row. A clickable row keeps its `onClick` in the feature's row, and the action buttons inside such a row call `stopPropagation` so a button click does not also fire the row action.
- Dates via `formatRelativeDate`, byte sizes via `formatBytes` (`@shared/utils/format`).
- Hide-and-hint for resource lists is module-owned: pass `canManage` (computed with helpers from `@features/machines/permissions`); when false, `ResourceList` hides the toolbar and renders the canonical hint — "You have read-only access to this machine. Ask an owner or admin for write access to manage its {resource}s." — carrying `{resource}s-permission-hint` and `data-permission="read"`. A list without a permission concept omits `canManage`: toolbar always, no hint. Never render a feature-private variant of the list hint and never ship disabled buttons.

## Streaming

- Every streaming endpoint rides the stream transport module (`@shared/streaming/streamTransport`); no feature hand-rolls a streaming fetch, an abort lifecycle, or a terminal guard. The two layers split by streaming shape: operation streams — a start/cancel lifecycle whose backend ends runs with a terminal `complete`/`error` event (image pull, quadlet auto-update) — use the `useNdjsonOperation` hook, which owns the abort, the supersede rule (a new start aborts the old run, whose late events reach nobody), exactly-one-terminal, and the running/error state; signal-driven follow streams without operation semantics (log following) call the `streamNdjson` function directly and pass their own `AbortSignal`. A feature keeps only its event handlers, shape guards, and invalidation choices — the Bearer preamble, the error envelopes, the abort teardown, and the NDJSON consume loop (malformed lines warned and skipped) are the module's. Blob downloads stay out: bytes carry no abort/supersede ritual and do not fit an NDJSON interface. Settled 2026-09-12 (architecture-review candidate C1).
- Log-bearing features ride the log-source factory (`@shared/streaming/logSource`): the feature's service resolves the machine-scoped path/url pair through the builder pair (`machineApiPath`/`machineApiUrl`) and exports a one-line `LogSource` builder handing both forms to `createLogSource` (`containerLogs`, `quadletLogs` are the reference adapters); the factory owns the rest of the log-endpoint ritual — the buffered tail fetch with its split-and-filter parse, the URLSearchParams follow query, and the `ApiError` wrap, with follow riding `followLogStream` on the stream transport. The `LogSource` contract and the buffered-logs DTO live in the kit; features keep only target resolution, and hand-concatenated log query strings are off-limits (`?tail=..&follow=true` died with the four twin functions). Feature logs suites keep one wiring smoke each — list renders, the logs button navigates to the logs page, the feature's own endpoint gets the request, history lines render — because tail/query/error invariants are pinned once in `logSource.test.ts` and viewer machinery once in `LogViewer.test.tsx`. The logs page picks its source from a record exhaustive over `LogKind`, so a future log-bearing kind is a type error until it gets an entry; URLSearchParams is the precedent for future stream query construction. Settled 2026-09-18 (architecture-review candidate C19).

## Auth and 401s

- "Refresh the session" has one owner, `refreshSession()` in `@shared/utils/api`: it alone assembles the POST literal, installs the fresh token, and holds the single flight every caller shares; success resolves the payload, any failure (auth rejection or network) resolves `null` without throwing or firing the seam. Its two thin callers are `AuthContext`'s default `resolveInitialState` resolver (mount restore) and `handleUnauthorized()` — only the 401 policy translates `null` into `fireSessionExpired()`, since a mount failure is logged-out, not session death. Never re-assemble a refresh elsewhere or keep a second vocabulary for the same act (`authApi.refresh` was deleted outright for exactly that). Settled 2026-09-18 (architecture-review candidate C18).
- 401s are owned by the shared session policy, never by a feature: the axios response interceptor on the shared instance (`@shared/utils/api`) and the stream transport both route through `handleUnauthorized` — single-flight refresh, replay once, session death when refresh or replay fails. The refresh/replay/seam semantics are pinned once in the shared suites (`shared/utils/api.test.ts`, `shared/streaming/streamTransport.test.tsx`, and the session-death wiring test in `App.test.tsx`); feature suites never pin 401 behavior or add their own expiry handling. File downloads stay outside the policy by decision.

## Tests

- Vitest + Testing Library + MSW. Global handlers in `src/test/handlers.ts` cover only auth/health/status; **each test overrides its endpoints with `server.use(http.get('*/api/...', ...))`** using a `*Fixture()` helper building a typed object with `Partial` overrides. Shared fixture factories live in `src/test/factories.ts` — import from there instead of re-declaring a `*Fixture()` per test file; add a new factory there when a DTO is first tested. Error envelopes come from `errorJson`/`errorResponse`/`axiosError` (`@/test/errors`), never hand-written literals. The harness-and-builders adoption arc is expand-then-adopt — owner first and pinned, then mechanical migration with assertions untouched; settled 2026-09-19 (architecture-review candidate C20).
- The full suite is a gate that must actually finish: it completes in under 2 minutes on a healthy tree (`npx vitest run`). During a change, run only the affected test files; run the full suite once at the end. A run that hangs or stretches past that is a bug to diagnose immediately, not a wait — a starved worker means an effect/async loop is blocking the event loop (see the LogViewer incident: unstable callback identities in a `useEffect` dep array).
- **List triad and hint behavior is pinned once, in `shared/components/ResourceList.test.tsx`**: mutual exclusion of the loading/error/empty/table states, plural testid derivation, the toolbar/hint swap, and the empty-copy override. A feature list suite keeps one loading smoke test (adapter wiring: the loading state renders with the toolbar still above it) plus all row/action/domain assertions; it consumes the derived testids as fixtures and does not re-pin exclusion.
- **Dialog skeleton and invariant behavior is pinned once, in `shared/components/MutationDialog.test.tsx`** (a stub mutation object, no QueryClient): reset on mount and unmount, cancel-sends-nothing, pending disables confirm, the default error region, close-on-success with the `onSuccess`/`onError` seams fired exactly once, and both replacement seams (`renderError`, `renderConfirm`). Feature dialog suites drop their skeleton re-pins (cancel, pending, generic in-modal error) and keep domain assertions: force/stop parameters, error-code hints and envelopes, row removal, toasts, navigate, read-user gating.
- **Stay-open report dialog behavior is pinned once, in `shared/components/PruneReportDialog.test.tsx`** (a stub mutation object, no QueryClient): reset on mount and unmount, the confirm/report footer swap, cancel-sends-nothing, stays-open-on-success, the report table and empty-report copy, the noun-derived copy, and the error region. Prune feature suites drop their report-detail re-pins (per-entry errors, empty-report copy) and keep read-level gating, one adapter-wiring smoke (opens the confirm, sends nothing), and the domain flow (request shape + list refetch through MSW).
- **Stream-transport invariants are pinned once, in `shared/streaming/streamTransport.test.tsx`**: Bearer header, content-type-only-with-body, non-ok and no-body envelopes, abort-is-not-an-error, supersede, exactly-one-terminal, and malformed-line skipping plus split reassembly. Feature streaming suites drop their transport re-pins and keep domain assertions: request shape, progress/report exposure, invalidation including the dry-run skip, error-event routing. Log-bearing feature suites stop at the one wiring smoke the Streaming section defines — log-event filtering and error-event parsing are pinned in the log kit and viewer suites, not theirs. One adapter-wiring smoke case per feature may stay even where the module also pins it (e.g. pull's non-ok envelope routing).
- Component and hook tests render through `renderWithQuery(ui, { router?, chakra? })` / `renderHookWithQuery` (`@/test/render`); never hand-roll a provider stack.
- Test seams are the public interface (hook return value, rendered DOM), never internals.
- Query invalidation is asserted at the factory test (`useListInvalidatingMutation.test.tsx`, the sanctioned `vi.spyOn(queryClient, "invalidateQueries")`); feature tests assert refetch through MSW instead of invalidation spies. Streaming-hook tests keep their invalidation spies — the dry-run skip is bespoke logic nothing else covers.
- **Multipart/upload endpoints: MSW cannot consume FormData bodies in this environment** — any handler that reads the body (`request.formData()`, `request.text()`, …) hangs, and axios POSTs of FormData hang with it. Instead: extract the payload building into a pure function (e.g. `buildPopulateForm`) and unit-test that; in component tests, mock the single API function with `vi.mock` (partial mock keeping the rest of the module real) and note why. See `volumesApi.populate.test.ts` + `VolumeList.populate.test.tsx`.
- Cross-realm caveat when asserting on parsed multipart parts outside this limitation: MSW parses bodies with its own `File`/`Blob` implementations, so `instanceof File` fails — check for `"name" in part` instead.
- AbortSignal cross-realm caveat: under jsdom, `AbortController`/`AbortSignal` globals are jsdom's, and Node >= 24 (undici 7) rejects them in `fetch` (`instanceof` brand check), while DOM listeners (framer-motion) reject Node's — so neither global swap works. `src/test/setup.ts` installs a fetch relay after `server.listen` that passes a Node-realm signal to the fetch stack; don't create `fetch` calls with hand-built signals that bypass it, and don't swap the globals back.

## Machine detail page

Tabs in `pages/MachineDetailPage.tsx`: Containers, Volumes, Images, Quadlets, Secrets, Settings. A new resource tab goes in epic-specified position; read-only slices take only `machineId`, permission-gated slices also take `effectivePermission(machine)`. The tab's list component is a `ResourceList` adapter — copy the smallest existing one (`SecretList`), never hand-roll list machinery.

DTO types and their field vocabularies (e.g. quadlet states: `unknown | stopped | running | error`; resources: container, pod, image, volume, network) are defined in each feature's `services/<feature>Api.ts` — read that file before writing tests or conditional UI against a resource's state.
