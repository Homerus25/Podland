# Frontend Conventions

How the React frontend (`frontend/src/`) is organized. System architecture lives in `docs/architecture-decisions.md`; domain language in `GLOSSARY.md`; API contracts in `doku/`. This file covers the patterns a new feature slice needs, so slices start from knowledge instead of re-reading sibling features.

Formatting is automated: a Crush pre-edit hook (`.crushrc` → `.crush/hooks/biome-format.sh`) runs Biome on a file before every edit, so files are already formatted when you read them. Run `npx biome check <changed files>` once at the end as a gate; never interleave `--write` runs with your own reads and edits.

## Feature folder layout

Each feature lives in `src/features/<name>/`:

- `services/<feature>Api.ts` — API client functions through the shared axios instance (`@shared/utils/api`), plus the **DTO response types colocated here** (see the DTO-types note at the end of this file). Host-scoped request URLs route through the builder pair `hostApiPath`/`hostApiUrl` (`@shared/utils/api`), the single owner of host-scoped URL construction: it percent-encodes every path segment, hostId first — services never hand-encode. Axios calls take the path form (the shared instance prepends the base); fetch consumers (stream transport, `downloadFile`) take the full form. Stream and download URLs are consumed from the owning service's export (`pullStreamUrl`, `autoUpdateStreamUrl`, `volumeExportUrl`), never re-derived in hooks or components, and importing `apiBaseUrl` outside `@shared/utils/api` is off-limits (module-private; the compiler enforces it). Settled 2026-09-15 (architecture-review candidate C11).
- `hooks/<feature>Api hooks` — React Query hooks in `use<Feature>.ts`.
- `components/` — UI components and their colocated tests.

## React Query

- Query keys come from the `shared/queries` constructors (`containersQueryKey`, `secretQueryKey`, `hostStatusQueryKey`, the `hostsQueryKey` constant, …); never build a `['hosts', …]` array or a private key constructor in a feature. A new resource tab adds one `HostResource` union member plus one plural list constructor in `queryKeys.ts`.
- List-invalidating mutations go through `useListInvalidatingMutation(hostId, resourceOrResources, run)` (`shared/queries`); cross-feature or streaming invalidation calls `invalidateHostResources(queryClient, hostId, resourceOrResources)`. The factory is host-scoped by design: an app-wide resource has no host to scope to, so a feature whose mutations invalidate one app-wide shared key keeps a feature-local invalidating-mutation wrapper over that key instead of forking the factory (`useUsersInvalidatingMutation` in `features/users/hooks/useUsers.ts` over `usersQueryKey` is the reference). No optimistic updates (matches backend "list reflects server state" simplicity).
- The freshness vocabulary is owned by the query-side factory in `shared/queries` (`useFreshQuery.ts`), the twin of the list-invalidating mutation factory. A view that must always show the host's current state (a detail view, an inspect reveal, a stats snapshot) rides `useOneShotQuery(key, fetcher, { enabled })` — zero gcTime so the cache entry dies with the view, with an optional enabled gate defaulting to true for lazy fetches. An always-fresh list rides `useAlwaysRefetchListQuery(key, fetcher)` — refetch on mount "always", so a lazy-tab re-entry issues a fresh request inside the app-wide stale window while the cached list stays visible (no loading flash). The key always comes from the shared constructors and the query result passes through untouched; never hand-assemble `gcTime` or `refetchOnMount` in a feature hook. Values that must never be cached (revealed secrets) travel through `useMutation`, not `useQuery`.

## Components

- Every table-backed resource list renders through `ResourceList` (`@shared/components/ResourceList`), the one owner of the list plumbing: the loading/error/empty/table triad, the Chakra table chrome, the plural testid derivation (`{resource}s-loading`, `-error`, `-empty`, `-table`), the toolbar wrapper, and the permission hint. The triad itself is single-owned one level down, in `ResourceStates` (`@shared/components/ResourceStates`) — the headless loading/error/empty owner `ResourceList` composes for its triad branch, and non-table collection sites (card grids, grant rows) render through it directly instead of hand-deriving the ritual. It renders the three states and takes `children` for the populated state, owning the triad JSX, the copy defaults, the styling, and the testid derivation; it is deliberately non-generic (`items: readonly unknown[] | undefined` — the module never reads item shape, and undefined counts as empty) and has no loading-copy override. It is for collections, not detail views: single-item loading/error with no empty semantics (host detail, quadlet edit, secret detail) does not fit `items`. Settled 2026-10-01 (2026-09-22 architecture-review candidate 8). A feature list is an adapter: it keeps its query and mutation hooks and hands over resolved state — `resource` (plural noun), `isPending`, `error`, `items`, `columns` (data, not JSX: `{ label?, isNumeric?, isName?, sortBy? }[]`; a label-less entry renders the bare action-column header), `renderRow`, and optionally `toolbar`, `canManage`, `emptyMessage`. Mobile pinning (spec 393) is module-owned off one marker: a list marks its name column with `isName`, and below `lg` the owner pins that column left and the trailing label-less action column right inside the table container's horizontal scroll — the pins reach the feature-rendered `<Td>`s (the owner clones the row's cells; spanning error cells are never pinned), so no feature hand-rolls sticky CSS. At `lg` and up the rendering is unchanged, and an unmarked list renders exactly as before. The pinning contract is pinned once in `shared/components/ResourceList.test.tsx`. `SecretList` (`src/features/secrets/components/SecretList.tsx`) is the smallest reference adapter; a new resource tab copies it, not the plumbing. Column sorting is module-owned: a column's optional `sortBy` accessor — `(item: T) => string | number` — extracts the row's sort key, and clicking a sortable header cycles asc, desc, unsorted (returning to the server's natural order); the first click on any column is asc, and there is no default sort. The active column carries `aria-sort="ascending"|"descending"` (unsorted columns carry no `aria-sort`) plus a direction arrow (▲ asc, ▼ desc); sortable headers get `cursor="pointer"` and `data-testid="sort-{resource}-{columnIndex}"`, while columns without `sortBy` (action columns) render as plain non-clickable headers. String keys compare with `localeCompare`, number keys numerically — the key's runtime type picks the comparison. Sort state is component-local and resets on unmount. Sort behavior is pinned once, in `shared/components/ResourceList.test.tsx` (the three-state cycle, the aria-sort contract, string and numeric reordering, non-sortable columns, the remount reset); each feature list suite keeps one smoke test — clicking a header reorders rows.
- The triad is **inline, never an early return**: the toolbar (or hint) renders above the state ternary, so toolbar and hint stay reachable while loading, on error, and when empty. Do not add a loading early-return to a list component.
- Errors render via `ErrorDisplay` with `getApiError(error)`; it accepts extra props (e.g. `data-testid`) and spreads them onto the alert. `ResourceList` uses it for the list-level error state; feature code keeps it for row- and dialog-level errors.
- Every mutation dialog renders through the shared dialog module at `@shared/components/MutationDialog`: form dialogs through its `FormDialog` preset, destructive confirms through its `ConfirmDialog` preset (ghost cancel, red confirm with the `confirm-delete-button` testid, pending wired). The module owns the plumbing every dialog used to hand-roll: the modal shell, the reset invariant (`reset()` runs on mount and unmount; consumers render the dialog conditionally, so mount is open and unmount is close, and reopening always starts clean), pending wiring, close-on-success, and the in-modal error region. It never touches react-query: the caller keeps its mutation hooks (and invalidation choices) and hands over the result's structural slice `{ mutate, isPending, error, isSuccess, reset }`. Settled 2026-09-11 (architecture-review candidate C6).
- Exception — a multi-phase chained flow that no `MutationDialog` preset fits (chained mutations with a read-only middle phase, where the phases share one modal and the footer changes per phase) is a feature-owned modal over the shared `Modal` shell (`@shared/components/Modal`), not a fork of the dialog module: the feature owns the phase state host, the per-phase footer, and the reset invariant (conditional render — mount is open, unmount is close — so reopening always starts clean), and keeps its mutation hooks and invalidation choices as usual. `AutoUpdateModal` (check-then-run report) and `ImportComposeModal` (spec #336: input → read-only preview → install report) are the precedents. Settled 2026-10-20 (spec #336 review).
- Stay-open report dialogs — a mutation whose success payload is rendered in place (prune) — ride `PruneReportDialog` (`@shared/components/PruneReportDialog`), standalone from `MutationDialog` because the two disagree on the headline invariant (stays open on success vs closes on success). It owns the reset lifecycle, the confirm/report footer swap, the report table (mono label cell, red error cell vs `formatBytes`), the empty-report and confirm copy derived from the singular `resource` noun, and the error region. The caller hands over the structural slice plus the success payload (`data: TEntry[]`), the noun, and the two entry accessors `entryKey` and `renderLabel`; the images prune adapter in `ImageList` is the smallest reference adapter. Toolbar labels stay feature-owned — they live outside the dialog.
- Stay-open transfer dialogs — a cross-host move/copy whose success narrates in place (quadlet, volume, secret, image) — ride the transfer-dialog preset at `@shared/components/TransferDialog`, the third dialog shape after `MutationDialog` and `PruneReportDialog` (issue 238's per-feature ruling ended when the third surface arrived; settled 2026-10-05, issue 241). The preset splits in two: `useTransferState(host, capability)` owns the state half — the capability-filtered target list (source excluded), the selected target defaulting to the first, and the mode defaulting to Move — and `TransferDialog` owns the render half: the target select, the mode radio (hidden when `pinnedMode` pins a copy-only surface — the image copy, issue 376), the target-scoped preview's pending/error/collision states, the referencing-quadlet warning, the confirm/report footer swap, and the in-modal error region with the `renderHints` seam (error-code hints live there, the `renderError` precedent). Like `PruneReportDialog` it stays open on success — a partial result names the both-hosts state — but the report node is the caller's: the adapter hands over `report` and decides what narrates, so a mixed success behavior (the quadlet's file-only close) stays feature-owned. The adapter calls `useTransferState` first (its preview hook needs `targetId`), keeps its domain in two body slots — `warnings` renders between the collision block and the referencing warning, `children` after it, preserving each surface's warning order — and passes `reset` only for a caller-owned mutation that outlives the dialog (component-local hooks die with it; the effect keys on the reference, so it is a react-query mutation's stable `reset`). The feature keeps its preview query key's constructor and fetcher and its mutation or stream hook as a thin adapter over the shared transfer-hooks module (`@shared/transfers`; settled 2026-10-13, issue 273, 2026-10-08 architecture-review candidate 5) — the module owns the preview ritual (the null-target guard, the empty-string placeholder key, the enabled gate), the both-hosts invalidation, and the move-stream lifecycle, while the feature keeps its domain: the event vocabulary, shape guard, progress fold, and URL builder. The hosts query inside `useTransferState` is the one query the preset owns. `MoveSecretDialog` is the smallest reference adapter. Settled 2026-10-19 (architecture-review candidate C6): a transfer adapter's domain splits into two colocated modules — the warnings module owns the pure preview projections and the warning lists as data-prop components (no queries, no hooks), and the report module owns the narration, the live progress, and the report precedence as an exported pure projection the adapter's close-on-success effect consumes — so the adapter keeps option state and confirm wiring only (`MoveQuadletDialog` is the reference split). Settled 2026-10-19 (architecture-review candidate C8): the transfer presentation rituals live in one module in the shared transfers kit (`@shared/transfers/transferPresentation`) — `transferProgressLabel` owns the phase vocabulary's labels (a skip without a reason renders plain "skipped", no dangling dash), and the `TransferReport` skeleton owns the stay-open report's shape (the Moved/Copied header with the optional byte-count suffix, the partial block with the pinned both-hosts tail and the red error line, the children slot) — while each adapter stays the wording owner of its domain cause sentence, narrations, and error-code hints (`MoveQuadletReport`, `MoveVolumeDialog`, and `MoveSecretDialog` are the reference adoptions).
- Raw inspect JSON — the read-only report behind a resource's detail page (containers, networks, images, secrets; spec 287) — rides the detail-page layout's "show inspect JSON" reveal, not a dialog: see the Detail pages section below for the module, its query-hook contract, and the `Record<string, unknown>` report type.
- The connect ritual — attaching a running container to a network — has one owner: `ConnectDialog` in the networks feature (`@features/networks/components/ConnectDialog`), discriminated by the fixed side (the Networks tab passes the network and the dialog picks the container; the Containers tab passes the container and the dialog picks the network). The dialog fetches its own options and drives the connect mutation itself, including the both-lists invalidation that rides the mutation; the two list surfaces shrink to a row button, the fixed side, and a close callback. The containers feature calls into the networks feature for connect, never the reverse, and the networks feature imports nothing new from containers for it. Settled 2026-10-13 (2026-10-08 architecture-review candidate 6).
- Side effects are explicit at each call site through the seams: `onSuccess` fires exactly once before the module closes the dialog (a toast, a navigate-away, or a silent close is a per-site choice, never a copy-paste accident), and `onError` fires on failure while the dialog stays open. A form's submit handler just calls `mutate`: forms no longer await their mutations and carry no internal error JSX or reset calls.
- The error region renders `ErrorDisplay` with `getApiError(error)` under the `mutation-dialog-error` testid by default; `renderError` replaces the whole region, and that is where error-code-to-hint mapping lives as feature adapters (volume composes the default display plus its in-use hint, populate maps `VOLUME_UPLOAD_TOO_LARGE`). On `ConfirmDialog`, `renderConfirm` replaces the confirm button itself (the force-refusal preset's swap, below).
- The force-refusal confirm ritual — a destructive delete the server can refuse with a specific error code (an in-use image, a pod with running containers) — has one owner: the `ForceConfirmDialog` preset in the shared dialog module, composing `ConfirmDialog`'s existing `renderError`/`renderConfirm` seams (no new seams; `ConfirmDialog`'s contract is unchanged). The preset owns the ritual: the refusal-code predicate, the orange hint replacing the error region (the shared `ErrorDisplay` for every other error), the confirm-to-force footer swap to the outline force button, the pending wiring, and the force flag keyed off the current error — the first confirm sends the plain request, and only after the refusal does the retry carry `force=true`. The adapter keeps its domain vocabulary only: the refusal code, the hint copy and its testid, the labels, the force button's testid, and the payload builder taking the force flag. The images delete modal and the pods remove modal are the reference adapters. Settled 2026-10-24 (2026-10-24 architecture review, ticket 358).
- The dialog module owns every confirm and form footer, extending the C6 settlement. Destructive confirms keep riding `ConfirmDialog`, now with `confirmColorScheme`/`confirmTestId` knobs so "confirm-with-variables" stops meaning "destructive" (defaults stay the red `confirm-delete-button` look, byte-identical). Confirms that perform a caller-owned action instead of a mutation ride `ActionDialog` — shell + ghost Cancel only: no pending wiring, no error region, no auto-close; the caller closes in `onConfirm` (the update-all pre-flight is the reference). Form dialogs ride `FormDialog` with fields-only bodies: the body's form carries the id and its submit handler just calls `mutate`; the footer's blue submit is associated by native form id, and one submit policy holds everywhere — disabled while the published form state (`FormValidityScope`, passed straight from the form library's `formState`) is invalid or submitting, or while the mutation is pending. The formerly ungated forms (create container, quadlet create/edit, add host) validate on change now, so their buttons start disabled — a deliberate normalization, not drift. The one non-dialog form site (the host settings inline form) joins through the composable `FormFooter` without a shell: it keeps submit-time validation, its submit gates on the host mutation's `pending` — the single prop the site keeps because its mutation lives in the host tab — and its Cancel (opt-in `cancelTestId`, `host-form-cancel` there) reverts the fields to the stored seed and fires the host's cancel seam, whose mutation reset clears both the error text and the "Changes saved" banner; cancel stays enabled while a save is in flight, and because a cancelled save still runs to completion server-side, the host tab suppresses that late settle so neither banner nor error resurrects over the reverted fields. Skeleton and invariant behavior of all these surfaces is pinned once in `shared/components/MutationDialog.test.tsx`; feature suites keep domain assertions only. Settled 2026-09-25 (2026-09-22 architecture-review candidates 3 and 7).
- The key/value row-editor ritual — the mono key/value inputs, the per-row remove buttons, and the add button over a `useFieldArray` — has one owner: `KeyValueEditor` (`@shared/components/KeyValueEditor`). The module renders the rows and buttons and owns the optional per-row key validation (`requireKeyWithValue`, default off: a key is required when the row's value is set). The rows-to-record mapper `keyValueRowsToRecord` (empty-key rows skipped, `undefined` when no row is filled, duplicate keys collapse to the last value) is the ritual's pure half and lives in `@shared/utils/keyValueRows` — its one owner — so the adapters and the payload builders in the feature services modules (which never import components) all import it from there. The adapter owns the form and `useFieldArray` and hands over the field-array return plus `register` and the per-row key error; the module never calls form hooks. Testids derive from a singular `noun` prop (`add-<noun>`, `remove-<noun>-<index>`), the add button's copy from `addLabel`, and the per-row aria labels from `keyAriaLabel`/`valueAriaLabel`/`removeAriaLabel`. The create-container page's environment rows, the create-volume dialog's labels and driver-options rows, and the create-pod dialog's labels are thin adapters over it. Row-editor behavior is pinned once in `shared/components/KeyValueEditor.test.tsx` (add/remove rows, testid and aria derivation, the validation gate on and off, mapper semantics); the feature suites keep domain assertions (payload shapes) plus one adapter-wiring smoke each. Settled 2026-10-19 (2026-10-19 architecture-review candidate C4).
- The structured row ritual — the non-key/value rows' chrome, the bind-mount flag mutual exclusion, and the labeled section block — has one owner: `RowEditor` (`@shared/components/RowEditor`), the sibling the key/value editor has for structured rows. This supersedes the C4 settlement's feature-local clause (the container page's non-key/value row chrome "stays feature-local"): that ruling predates the pods feature, and the create-pod dialog's verbatim copy of the chrome was the second implementation — the drift case the cross-domain duplication ruling says triggers extraction (the copies had already diverged: the page's row input carried a type prop the dialog's copy dropped). The module owns the ritual: the row list editor over a field array (the per-row remove button, the add button, the noun-derived `add-<noun>`/`remove-<noun>-<index>` testids, the remove-aria derivation, and the optional `addArea` slot beside the add button for sibling actions — the inline volume create is the consumer), the row input and select controls (mono, type, placeholder, aria), the labeled section block, and the bind-mount z/Z/U flags with their mutual exclusion (checking z unchecks Z and vice versa; U stays independent), the flags' copy module-owned. The adapter contract is the key/value editor's: the surface keeps the form, the field arrays, register, and watch/setValue, and hands over the field-array return, the copy, and the row's controls through a per-row render seam — the row shape (which fields, which options) and its copy stay the feature's; the module never calls form hooks. The create-container page (ports, bind mounts, named volumes, devices, capabilities) and the create-pod dialog (bind mounts, named volumes) are the adapters. The checkbox-list selection toggle is absorbed by `CheckboxList` itself (a next-selection `onSelect` callback; the copied toggle helpers died with it). Settled 2026-10-24 (2026-10-24 architecture review, ticket 369).
- Reference adapters: `SecretList`'s delete confirm is the smallest confirm; `HostsPage`'s add-host modal is the smallest form host. Copy those, not the plumbing. Non-modal mutation sites (secret reveal, share grant/revoke, the pull-image toolbar) keep feature-local resets; they share no dialog skeleton with the module — the host settings inline form is the exception that rides the composable `FormFooter` (2026-09-25 settlement above).
- Rows are feature-rendered: the Row component owns the singular `data-testid` (`<item>-row`) so tests use `within(row)` for per-row assertions. When several of a list's rows render on one page (the users directory), the testid carries the row's unique key — `user-row-${username}`, the `grant-row-${id}` precedent — so tests still select one row. A clickable row keeps its `onClick` in the feature's row, and the action buttons inside such a row call `stopPropagation` so a button click does not also fire the row action.
- Dates via `formatRelativeDate`, byte sizes via `formatBytes` (`@shared/utils/format`).
- Hide-and-hint for resource lists is module-owned: pass `canManage` (computed with `can(host, capability)` from `@features/hosts/permissions`, one predicate over the capability table mirroring the backend's enforcement); when false, `ResourceList` hides the toolbar and renders the canonical hint through the shared `PermissionHint` (`@shared/components/PermissionHint`) — "You have read-only access to this host. Ask an owner or admin for write access to manage its {resource}s." — carrying `{resource}s-permission-hint` and `data-requirement="write"`. `PermissionHint` owns every hint sentence, the derived `{scope}-permission-hint` testid, and the `data-requirement` attribute (write, admin, owner); never render a feature-private variant of any hint and never ship disabled buttons. Every host-scoped list whose resource has write-level routes has a permission concept and passes `canManage` — containers included: its create/start/stop/delete routes are write-gated, so a read-level grantee gets the hint, not the toolbar. A read-only slice (no mutation routes yet) takes only `hostId` and passes no `canManage` — no hint, ever; `NetworkList` is the reference adapter.

## Streaming

- Every streaming endpoint rides the stream transport module (`@shared/streaming/streamTransport`); no feature hand-rolls a streaming fetch, an abort lifecycle, or a terminal guard. The two layers split by streaming shape: operation streams — a start/cancel lifecycle whose backend ends runs with a terminal `complete`/`error` event (image pull, quadlet auto-update) — use the `useNdjsonOperation` hook, which owns the abort, the supersede rule (a new start aborts the old run, whose late events reach nobody), exactly-one-terminal, and the running/error state; signal-driven follow streams without operation semantics (log following) call the `streamNdjson` function directly and pass their own `AbortSignal`. A feature keeps only its event handlers, shape guards, and invalidation choices — the Bearer preamble, the error envelopes, the abort teardown, and the NDJSON consume loop (malformed lines warned and skipped) are the module's. Blob downloads stay out: bytes carry no abort/supersede ritual and do not fit an NDJSON interface. Settled 2026-09-12 (architecture-review candidate C1).
- Log-bearing features ride the log-source factory (`@shared/streaming/logSource`): the feature's service resolves the host-scoped path/url pair through the builder pair (`hostApiPath`/`hostApiUrl`) and exports a one-line `LogSource` builder handing both forms to `createLogSource` (`containerLogs`, `quadletLogs` are the reference adapters); the factory owns the rest of the log-endpoint ritual — the buffered tail fetch with its split-and-filter parse, the URLSearchParams follow query, and the `ApiError` wrap, with follow riding `followLogStream` on the stream transport. The `LogSource` contract and the buffered-logs DTO live in the kit; features keep only target resolution, and hand-concatenated log query strings are off-limits (`?tail=..&follow=true` died with the four twin functions). Feature logs suites keep one wiring smoke each — list renders, the logs button navigates to the logs page, the feature's own endpoint gets the request, history lines render — because tail/query/error invariants are pinned once in `logSource.test.ts` and viewer wiring once in `LogViewer.test.tsx`. The logs page picks its source from a record exhaustive over `LogKind`, so a future log-bearing kind is a type error until it gets an entry; URLSearchParams is the precedent for future stream query construction. Settled 2026-09-18 (architecture-review candidate C19).
- The logs **route** contract is one kit, `@shared/logs/logRoute`: it owns the `LogKind` union with its `isLogKind` guard, the `LOG_ROUTE_PATTERN` route constant (mounted by the app router and by both feature logs test renderers — no logs route or path literal lives outside the kit), the `logsPath` builder (percent-encodes `hostId` and `targetId`, extending the C11 host-scoped URL discipline to the one host-scoped URL family it did not cover; the router decodes params on the far side), the typed `LogsPageState` navigation state, and the `useOpenLogs(hostId, kind)` hook that binds the kind once per feature — the twin `useOpenContainerLogs`/`useOpenQuadletLogs` hooks died with it. A new log-bearing kind is one `LogKind` member plus one `LOG_SOURCES` entry in the logs page. The C19 `logSource` kit is untouched by design: that kit owns fetching, this one owns navigation (the `LOG_SOURCES` record stays with the logs page because it needs the feature services; the dependency direction stays features → shared). The path shape and the encoding round trip are pinned once in the kit's suite. Settled 2026-10-01 (2026-09-22 architecture-review candidate 9).

## Auth and 401s

- "Refresh the session" has one owner, `refreshSession()` in `@shared/utils/api`: it alone assembles the POST literal, installs the fresh token, and holds the single flight every caller shares; success resolves the payload, any failure (auth rejection or network) resolves `null` without throwing or firing the seam. Its two thin callers are `AuthContext`'s default `resolveInitialState` resolver (mount restore) and `handleUnauthorized()` — only the 401 policy translates `null` into `fireSessionExpired()`, since a mount failure is logged-out, not session death. Never re-assemble a refresh elsewhere or keep a second vocabulary for the same act (`authApi.refresh` was deleted outright for exactly that). Settled 2026-09-18 (architecture-review candidate C18).
- 401s are owned by the shared session policy, never by a feature: the axios response interceptor on the shared instance (`@shared/utils/api`) and the stream transport both route through `handleUnauthorized` — single-flight refresh, replay once, session death when refresh or replay fails. The refresh/replay/seam semantics are pinned once in the shared suites (`shared/utils/api.test.ts`, `shared/streaming/streamTransport.test.tsx`, and the session-death wiring test in `App.test.tsx`); feature suites never pin 401 behavior or add their own expiry handling. File downloads stay outside the policy by decision.

## Tests

- Vitest + Testing Library + MSW. Global handlers in `src/test/handlers.ts` cover only auth/health/status; **each test overrides its endpoints with `server.use(http.get('*/api/...', ...))`** using a `*Fixture()` helper building a typed object with `Partial` overrides. Shared fixture factories live in `src/test/factories.ts` — import from there instead of re-declaring a `*Fixture()` per test file; add a new factory there when a DTO is first tested. Error envelopes come from `errorJson`/`errorResponse`/`axiosError` (`@/test/errors`), never hand-written literals. The harness-and-builders adoption arc is expand-then-adopt — owner first and pinned, then mechanical migration with assertions untouched; settled 2026-09-19 (architecture-review candidate C20).
- The full suite is a gate that must actually finish: it completes in under 2 minutes on a healthy tree (`npx vitest run`). During a change, run only the affected test files; run the full suite once at the end. A run that hangs or stretches past that is a bug to diagnose immediately, not a wait — a starved worker means an effect/async loop is blocking the event loop (see the LogViewer incident: unstable callback identities in a `useEffect` dep array).
- **List triad behavior is pinned once, in `shared/components/ResourceStates.test.tsx`**: mutual exclusion of the loading/error/empty/children states, plural testid derivation, the default and overridden empty copy, children-only-when-populated, and undefined = empty. `shared/components/ResourceList.test.tsx` keeps the toolbar/hint swap, the columns/chrome pins, and one composition smoke (the triad routing through `ResourceStates`). A feature list suite keeps one loading smoke test (adapter wiring: the loading state renders with the toolbar still above it) plus all row/action/domain assertions; it consumes the derived testids as fixtures and does not re-pin exclusion.
- **Dialog skeleton and invariant behavior is pinned once, in `shared/components/MutationDialog.test.tsx`** (a stub mutation object, no QueryClient): reset on mount and unmount, cancel-sends-nothing, pending disables confirm, the default error region, close-on-success with the `onSuccess`/`onError` seams fired exactly once, both replacement seams (`renderError`, `renderConfirm`), and the force-refusal preset's ritual (the refusal-code hint replaces the error region, non-refusal errors render through the shared `ErrorDisplay`, the footer swaps to the outline force button, pending wiring holds, and the force flag keys off the current error). - **Multipart/upload endpoints: MSW cannot consume FormData bodies in this environment** — any handler that reads the body (`request.formData()`, `request.text()`, …) hangs, and axios POSTs of FormData hang with it. Instead: extract the payload building into a pure function (e.g. `buildPopulateForm`) and unit-test that; in component tests, mock the single API function with `vi.mock` (partial mock keeping the rest of the module real) and note why. See `volumesApi.populate.test.ts` + `VolumeList.populate.test.tsx`.
- **Complex form-to-payload mappings are pure builders in the feature's services module** — a dialog's form-values-to-request mapping lives as an exported pure function next to the DTO types it produces, unit-tested there without a DOM; the dialog keeps form ownership only (react-hook-form wiring, field arrays, checkbox toggling, section composition, JSX) and its submit handler maps through the builder. The form-values shape and its row interfaces move to the services module with the builder, keeping the dependency direction one-way (the dialog imports them; the services module never imports components). `buildCreateContainerInput` in `containersApi.ts` is the reference (spec 313 dialog); `buildMoveInput` (quadlets) and `buildPopulateForm` (volumes) settled the pattern. This generalizes the upload payload-builder rule above from multipart endpoints to complex form payloads. Settled 2026-10-19 (architecture-review candidate C3).
- Cross-realm caveat when asserting on parsed multipart parts outside this limitation: MSW parses bodies with its own `File`/`Blob` implementations, so `instanceof File` fails — check for `"name" in part` instead.
- AbortSignal cross-realm caveat: under jsdom, `AbortController`/`AbortSignal` globals are jsdom's, and Node >= 24 (undici 7) rejects them in `fetch` (`instanceof` brand check), while DOM listeners (framer-motion) reject Node's — so neither global swap works. `src/test/setup.ts` installs a fetch relay after `server.listen` that passes a Node-realm signal to the fetch stack; don't create `fetch` calls with hand-built signals that bypass it, and don't swap the globals back.

## Host detail page

The host's eight areas (Containers, Volumes, Images, Networks, Quadlets, Pods, Secrets, Settings) live in the left navigation as a second section below the main links (issue 459): the vocabulary and the route→tab derivation are owned by `features/hosts/hostNav.ts` (`HOST_TABS`, `resolveHostTabKey`, `hostNavScope`), the sidebar section by `HostNavSection`, and the header's host identity by `HostHeaderIdentity` — the header shows the host name with its permission badge plus endpoint, ssh user, and the live podman version on one wrapping row on every `hosts/:hostId/*` route, nothing while the host query is pending, the "Hosts" title on a failed fetch. A new resource tab goes in epic-specified position; read-only slices take only `hostId`, permission-gated slices take the `host` and gate with `can(host, capability)`. The tab's list component is a `ResourceList` adapter — copy the smallest existing one (`SecretList`), never hand-roll list plumbing. `pages/HostDetailPage.tsx` renders only the active tab's panel — no heading, no info row, no tab strip: a `?tab=<key>` search parameter (the `HOST_TABS` order) selects the panel; an unknown or missing value falls back to Containers. Switching tabs is a navigation through the sidebar links, so a panel mounts on arrival and unmounts on leave: the tab's endpoint fires on first activation, not at page open, and because a list's sort state is component-local, it resets on re-entry. The host's own query stays eager — the permission gating needs it — and the default tab (Containers) still loads on page open. The Settings tab's access-grants query rides the same laziness; its owner-only gating is unchanged. Every tab activation issues a fresh request: the eight host-scoped tab queries (the seven resource lists plus the settings tab's access grants) ride `useAlwaysRefetchListQuery`, the freshness factory's always-refetch list flavor, so a re-entry refetches even inside the app-wide five-minute stale window while the cached list stays visible (no loading flash — the fresh list lands over the cached one). Deliberately distinct from the one-shot flavor (`useOneShotQuery`) the detail views ride: a remounting panel would flash loading under the one-shot rule. The containers and networks hooks are feature-shared, so the connect and create-network dialogs gain the same fresh fetch on every open — intended, their option lists stay current. Active-state rules: the "Hosts" main-nav link is active only on the `/hosts` list page; on host-scoped routes the matching host tab is active, including on detail sub-pages and the logs page (the tab matching the logs target's kind).

DTO types and their field vocabularies (e.g. quadlet states: `unknown | stopped | running | error`; resources: container, pod, image, volume, network) are defined in each feature's `services/<feature>Api.ts` — read that file before writing tests or conditional UI against a resource's state.

## Detail pages

Resource detail pages (spec 301) — one routed page per host resource under `/hosts/:hostId/<resource>/:<id>` — ride one shared layout, `@shared/components/DetailPage`. The module owns the page shell and never touches react-query: the header with the item's display name and a back button, the overview slot for the resource's label/value rows (`children`), the "show inspect JSON" collapsible at the bottom (toggle button, scrollable monospace pretty-printed report, copy-to-clipboard button), and the loading/error/not-found states (spinner + "Loading..." while the overview query is pending, `ErrorDisplay` with `getApiError` on error, "This item no longer exists on the host." on 404). The page adapter hands over the slices: `title`, `backTo`, `isPending`, `error`, `notFound`, the inspect query's structural slice (`inspectQuery` — the module's exported `InspectQuerySlice` shape `{ isPending, error, data }`), and the reveal state (`revealed`, `onToggleInspect`).

- **Per-resource adapter** — each detail page lives in its feature folder at `features/<resource>/components/<Resource>DetailPage.tsx`, reads its route params via `useParams`, owns its queries, and renders `DetailPage`. The routes sit in `App.tsx` under the protected layout, next to `hosts/:hostId`.
- **Query key scheme** — the overview query uses the singular detail key (`containerQueryKey`, `volumeQueryKey`, `imageQueryKey`, `networkQueryKey`, `secretQueryKey`) and rides `useOneShotQuery`, the freshness factory's one-shot flavor, so every page visit refetches.
- **Lazy inspect fetch** — the page owns a `revealed` state and passes `enabled: revealed` to the inspect hook (`useContainerInspect` and its siblings take an optional `{ enabled }` param; the volume reveal rides `useVolume`, whose response is the volume's inspect DTO). The inspect request fires on the first "Show inspect JSON" click, never on page mount.
- **Cross-links** — related resources link to their detail pages: a container's image name to `/hosts/:hostId/images/:imageId`, a container's secrets to `/hosts/:hostId/secrets/:secretId`, a network's attached containers to `/hosts/:hostId/containers/:containerId`.
- **History-aware back button (spec 373)** — the back button returns to the page the user came from. When the router has in-app history (the current location is not the session's initial entry — the `useHasInAppHistory` predicate in the detail-route kit, riding react-router's contract that a history's initial entry carries the key `"default"`), Back navigates back through the history stack exactly like the browser's back button, returning to the referring page; the accepted trade-off is that this branch is a click handler, not a real link (no middle-click/open-in-new-tab). When there is no in-app history (deep link, bookmark, fresh tab), Back stays a real link to `/hosts/:hostId?tab=<resource>` (the spec 297 `?tab=` deep link). Scope: the shared layout's back button only — the create-container page's cancel (spec 341) and the logs page's back button are unchanged.
- **Detail-page capability gating has one owner: `useCapabilityGate(hostId, capability)`** (`@features/hosts/hooks/useCapabilityGate`), the detail-page twin of the list-side `canManage` pattern — lists receive their host eagerly from the parent page, detail pages must fetch it, so the pending state exists only because of that fetch. The hook lives in the hosts feature, beside the capability vocabulary it reads: it composes the host detail query with the capability predicate (`can`, which stays pure — no React, no queries) and owns the whole classification, so no page re-derives it or drops the error branch a hand-rolled copy can silently lose. Its answer is a tri-state enum: `pending` while the host query is in flight (the caller's level is unknown), `allowed`, `denied` — with a failed host query classified as denied (the error-is-denied policy, owned once here). Every gated affordance on a details page renders from the enum: pending renders neither control nor hint (never flash the read-only hint at a write-capable caller), allowed renders the control, denied renders the shared permission hint through `PermissionHint` — the hint's copy (scope, requirement, resource) stays caller-owned domain vocabulary; the hook owns only the classification. Affordances whose established pattern renders no hint (the container page's edit-configuration header action) consume the same enum — allowed renders, otherwise nothing. The classification is pinned once in the hook's suite (pending, allowed, denied, error-is-denied); feature suites keep adapter-wiring smokes only (allowed renders the control, denied renders the hint, pending renders neither) and never re-pin the policy. The container details page is the reference adapter. Settled 2026-10-30 (spec #437 architecture review).
